Linux 的调度机制

调度过程

Linux 内核的调度对象是线程，而不是进程。

典型的调度过程如下：

  ↓

  ↓

  ↓

  ↓

调度发生的常见原因包括：

  1. 线程主动让出 CPU，例如线程等待网络、磁盘或锁时，会进入睡眠状态，让 CPU 去运行其他线程。
  2. 当更高优先级线程变为可运行状态时，调度器可能立即抢占当前线程。为什么说“可能”呢？因为抢占是否立即发生，取决于内核抢占配置以及当前是否处于不可抢占的内核上下文。
  3. 线程消耗了足够的运行时间。
  4. 内核或硬件事件触发，例如时钟中断、I/O 完成、中断处理等事件。

调度策略与优先级

常见的调度策略包括：

调度策略 适用场景
SCHED_OTHER 普通后台和应用线程
SCHED_FIFO 实时线程，先进先出
SCHED_RR 实时线程，带时间片轮转
SCHED_DEADLINE 有明确时间约束的任务
SCHED_IDLE 尽可能低优先级的后台任务

普通线程通常使用 SCHED_OTHER，它只办三件事——公平、公平、还是他妈的公平。在 Linux 6.6 以前的内核中由 CFS（Completely Fair Scheduler）调度器实现，在 Linux 6.6 以后的内核中由 EEVDF（Earliest Eligible Virtual Deadline First）调度器实现，这俩最大的区别是，EEVDF 在 CFS 的基础上加入了延迟敏感度，既保证公平也保证响应速度。

SCHED_FIFO 和 SCHED_RR 为实时调度策略，相较于普通调度策略优先级更高。FIFO 策略在线程阻塞、主动让出 CPU，或被更高实时优先级的线程抢占前将一直执行；RR 策略则为同一优先级的线程分配时间片，时间片用尽后轮转到队列末尾。

优先级从高到低：

那么相同调度策略下，如何区分线程调度的优先级呢？根据普通调度和实时调度，分为 nice 和实时优先级两种不同的概念。

  • nice：调整普通线程之间的相对权重，范围在 -20 ~ 19。
  • 实时优先级：决定实时线程之间的调度层级，范围在 1 ~ 99；实时线程整体上优先于普通线程。

在内核内部，实时调度策略的优先级高于普通调度策略；nice 值只用于比较普通调度策略下线程的相对权重。

如何手动控制线程调度策略和优先级？

对于 std::thread，我们可以通过 pthread_setschedparam 函数设置线程调度策略和优先级，示例：

// 函数原型
int pthread_setschedparam(pthread_t thread,
                          int policy,
                          const struct sched_param *param);

void worker() {
  pthread_t tid = pthread_self();
  int policy = SCHED_FIFO;
  struct sched_param param;
  param.sched_priority = 50;
  int ret = pthread_setschedparam(tid, policy, &param);
  if (ret) {
    // 处理错误码
  }
}

在使用它时最常见的问题就是 Operation not permitted，这需要我们提权，例如在 Docker 中我们必须有 cap_sys_nice 权限。有时还与其他内核参数相关，例如 /proc/sys/kernel/sched_rt_runtime_us，当值为 950000 时，线程调度策略与优先级可能会设置失败，必须改为 -1 才行。

调度开销

公平的调度是有代价的，上下文切换、线程迁移占了大头。

上下文切换（Context Switch）过程中包含了保存和恢复寄存器、运行队列维护、调用状态更新等操作，高频的上下文切换会增加内核调度开销，并可能放大锁竞争和缓存失配。线程迁移不一定伴随每次上下文切换；线程跨核迁移时，目标 CPU 通常没有原 CPU 上已经建立的工作集，可能产生更多 L1/L2 Cache miss，增加访存延迟。

优化方向

在生产过程中，偶尔能遇到调度引起的实时性问题，其本质在于“有限且不可再生” 的硬件资源（CPU 时间片、Cache、物理核）与 “动态且诉求多样” 的软件需求（低延迟、高吞吐、强实时）之间的供需矛盾。因此合理的架构、程序设计和资源分配尤为重要。

场景 主要问题 优先优化方向
CPU 密集型、多线程 线程过多、迁移、缓存局部性 控制线程数，减少迁移，合理绑核
任务粒度很小 上下文切换和调度次数过多 批处理、合并任务、增大任务粒度
I/O 密集型 锁等待、唤醒、I/O 延迟 优化同步模型和 I/O 路径
实时任务 抢占和唤醒延迟 优先级、CPU 隔离、IRQ affinity
NUMA 服务器 远程内存访问 CPU 与内存节点绑定
容器环境 CPU 竞争或 quota throttling cgroup/cpuset 和配额配置

CPU 亲和性

CPU 亲和性（CPU Affinity）本质上是线程属性，表示限制一个线程只能在哪些 CPU 上运行，下面也称为“绑核”。如果希望约束一个进程的所有线程，需要逐个设置线程的 affinity，或者使用 cgroup 对整组线程进行约束。

CPU 亲和性又分为软亲和和硬亲和：

  • 软亲和：调度器尽最大努力让线程留在上次运行的 CPU 核心上，但在各核心负载不均时，仍会将线程搬移到空闲核心。
  • 硬亲和：由用户或应用程序通过 CPU 掩码（CPU Mask）显式设定。操作系统调度器不会将该线程调度到掩码范围之外的 CPU；实际可运行范围还会受到 cgroup、cpuset 和 CPU 在线状态等限制。

这个很好理解，如上所述，有时我们希望减少线程跨核迁移，就可以把进程或者线程绑定在特定的核心上。

如何手动控制 CPU 亲和性？

进程

对于进程，这里介绍通过 cgroup 进行绑核的方法，使用 cgroup 还能控制进程的内存占用上限，功能强大。

cgroup（Control Groups）是 Linux 内核提供的资源管理机制，用于把一组进程组织起来，并统一限制或统计它们的资源使用。通过对不同 controller 的设置，可以控制 CPU 使用权重、配额和可用 CPU，内存上限和 swap，I/O 带宽等资源。

cgroup 分为 v1 与 v2 版本，可以通过 stat -fc %T /sys/fs/cgroup/ 命令初步区分：输出为 cgroup2fs 通常表示 v2；v1 通常表现为各 controller 的独立挂载。v1 的使用较为复杂，使用多个层级和多个 controller，v2 使用统一层级，详细区别可看 Linux 文档，这里先介绍 v1 一下的绑核方式。

其实非常简单，只要在 cpuset controller 中创建 group，设置 CPU 亲和性，最后将 PID 写入 group 中即可。

bash

# 创建组
sudo mkdir /sys/fs/cgroup/cpuset/cg1
# 设置可用的内存节点
echo 0 | sudo tee /sys/fs/cgroup/cpuset/cg1/cpuset.mems
# 绑定 CPU 2 和 CPU 3
echo 2-3 | sudo tee /sys/fs/cgroup/cpuset/cg1/cpuset.cpus
# 加入进程
echo <PID> | sudo tee /sys/fs/cgroup/cpuset/cg1/tasks

# 启用 cpuset controller
echo "+cpuset" | sudo tee /sys/fs/cgroup/cgroup.subtree_control
# 创建组

# 设置可用的内存节点
echo 0 | sudo tee /sys/fs/cgroup/cg2/cpuset.mems
# 绑定 CPU 2 和 CPU 3
echo 2-3 | sudo tee /sys/fs/cgroup/cg2/cpuset.cpus
# 加入进程
echo <PID> | sudo tee /sys/fs/cgroup/cg2/cgroup.procs

需要注意的是，如果需要删除 group，应该使用 rmdir 命令，而不是 rm -rf 命令。另外在设置时需要确保有相应的权限。

// 函数原型
int pthread_setaffinity_np(pthread_t thread,
                           size_t cpusetsize,
                           const cpu_set_t *cpuset);

void worker() {
  pthread_t tid = pthread_self();
  cpu_set_t cpuset;
  // 绑定 cpu0 和 cpu1
  CPU_ZERO(&cpuset);
  CPU_SET(0, &cpuset);
  CPU_SET(1, &cpuset);
  int ret = pthread_setaffinity_np(tid, sizeof(cpuset), &cpuset);
  if (ret) {
    // 处理错误码
  }
}
